# electron/knowledge-index.cjs

Source: [`electron/knowledge-index.cjs`](../../../electron/knowledge-index.cjs)

Ranked text search over the project documents, built on SQLite FTS5 through `node:sqlite` (still experimental in Node, which is why this is the only module that knows about SQLite). It is a derived index: the files stay the source of truth, and a database that is corrupt or of another `SCHEMA_VERSION` is deleted and rebuilt. It complements [project-search.cjs](project-search.cjs.md), which stays the tool for exact text and regular expressions.

A document is split by `chunkMarkdown` into passages along its Markdown headings (those inside fenced code do not count); a section longer than 250 words is split by paragraph, and a single huge paragraph by sentence. Each passage keeps the path of its headings (`Book › Chapter 1 › Scene`) and the 1-based line range in the file, so the reader can quote it and open it with `read_file` (`startLine` / `endLine`). A YAML header at the top of a file (between two `---` lines, like the one of the saved web pages) is metadata, not text: it is skipped (the line numbers stay the same). A section without text produces no passage, and neither does a paragraph without a single letter or digit (`###`, `---`, `***`, an empty table row): it says nothing and, inheriting the headings, it climbed the results. Embedded images (`data:image/png;base64,…`, often hundreds of thousands of characters on one line, typical of the `[image1]: <data:…>` definitions of exported documents) are not text: they are replaced with `…` before chunking (the line numbers do not change), so they are neither searched nor embedded. Passages indexed before this stay as they were until their file changes or the index is rebuilt; the embedders cut the text anyway. File paths are relative to the project root, with `/`.

- `createKnowledgeIndex({ file, readOnly })`: opens (or creates) the database; with `readOnly: true` (used by the MCP server while the app writes) it only searches: it never creates, rebuilds or deletes the file, and fails if it is missing or of another schema version; `':memory:'` in tests. WAL mode with a 5 s busy timeout, so the app can write while the MCP server reads. Every operation takes the project (any stable string, normally its root) so that several projects can share one file.
  - `indexFile(project, relative, text, { mtimeMs, size })`: indexes or re-indexes a document inside one transaction; unchanged text (SHA-1) only refreshes date and size. Returns `{ changed, chunks }`.
  - `removeFile`, `removePath(project, relative)` (a file or a whole folder), `clearProject`, `movePath(project, from, to)` (rename or move: passages are kept, only paths change; whatever was at the destination is discarded), `listFiles(project)` (`Map` path → `{ mtimeMs, size }`, to decide what to re-read after a scan), `stats(project)` (`{ files, chunks, updatedAt }`), `close()`.
  - `search(project | [projects], query, { limit, folder, maxPerFile })` → `{ mode, results }`; with several projects (the project and its reference folders) `folder` is ignored and every result says which one it comes from; each result `{ project, path, heading, startLine, endLine, snippet, score }`. First all the words (the last one as a prefix), and if nothing is found at least one (`mode: 'or'`). BM25 with the headings weighted five times the text; accents and case do not matter (`unicode61 remove_diacritics 2`). `folder` restricts to a folder or file; `maxPerFile` (default 3) keeps one document from filling the list; `limit` defaults to 10, 50 at most. The snippet marks the matches with « ».
- **Chunker version** (`CHUNKER_VERSION`, now 3, in `meta.chunker`): when the way documents are split changes, opening the database clears the files' hash and date, so the next scan re-reads every file; the vectors of passages that stay identical are reused (they are tied to the text), the others are recomputed and the orphans pruned.
- `buildMatchQuery(input, mode)`: the words typed → an FTS5 expression. Every word is quoted, so punctuation and FTS5 operators (`NEAR`, `OR`, `*`, `:`) typed by the user never reach the query syntax; a phrase in double quotes stays a phrase; at most 12 terms.
- `isAvailable()`: whether `node:sqlite` exists in this Node (callers fall back to `search_files` when it does not).

**Search by meaning (vectors)**: `chunks.hash` (SHA-1 of the passage text with its headings, the text that is embedded) and the table `embeddings (model, hash, vector)`: one 384-float vector per distinct text **and per model**, so a passage that does not change between two indexings is not recomputed, identical texts share a vector, and two models (CPU q8 and graphics card fp16) live side by side: switching from one to the other only computes what the other lacks. Like everything here it is derived and rebuilt from the files. `SCHEMA_VERSION` is 3; opening a version 2 database does not drop it: its vectors move under the model they were computed with (`meta.embedding_model`).
  - `pendingEmbeddings(projects, model, limit)` returns `[{ hash, text }]` still without a vector for that model, `storeEmbeddings(model, [{ hash, vector }])`, `pruneEmbeddings()` (vectors, of any model, of passages that no longer exist), `clearEmbeddings(model?)` (one model, or all), `embeddingStats(projects, model)` returns `{ total, embedded }`.
  - `search(..., { queryVector, model })`: with the vector of the question (computed by the worker with the same model) the passages are also ranked by similarity with the vectors **of that model** (exhaustive dot product, a few ms for thousands of passages: sqlite-vec's `vec0` does the same brute force, so it is not needed) and the two lists are merged with Reciprocal Rank Fusion (`fuseRanked`: each passage scores the sum of 1/(60 + rank) in every list, so BM25 and similarity scales never have to be compared). The result has `mode: 'hybrid'` and each result `via`: `words`, `meaning` or `both`. In hybrid mode the "at least one word" fallback is not used (a common word like "di" or "per" would raise unrelated passages); a vector-only passage has a plain snippet (its first words). E5 similarities are compressed (about 0.77 to 0.85), so there is no absolute cut-off: results are "best first". Vectors of another dimension are ignored.
  - The MCP server opens the index read-only and has no embedder: with the app closed it keeps searching by words (with the app open the search goes through the app, see [mcp-server.cjs](mcp-server.cjs.md)).


Tests: [tests/knowledge-index.test.cjs](../../../tests/knowledge-index.test.cjs), run with `npm run test:unit` (also part of `npm test`).

**Relevance of the meaning side.** Text models give similarities in a narrow range (about 0.75-0.90), so even a question with no answer has its "nearest" passages at 0.83 and a fixed threshold does not hold. `relevantNeighbors` judges each question against itself: the search already compares the question with every vector, and it also keeps their mean and standard deviation, so a passage gets a score `z` (how far above the mean it stands). With words that found something, neighbours count from z 3; with no word in common they count from z 3.5 but only if at least three passages stand above z 4 (a group that detaches, not one lucky case); otherwise the meaning side returns nothing, and so does the search if the words found nothing ("Tardigrado" no longer returns ten random passages). With fewer than 60 vectors nothing is judged. In the "at least one word" fallback the function words (di, della, the, el…) are ignored (`STOPWORDS`), unless the question is made only of them, and those partial matches are fused with the meaning side (`partial: true` when no passage has all the words). Each result says `via`: `words`, `meaning` or `both`.

**Relevance factor.** The group of passages standing above z 4 is always required, also when a word was found (a word that appears by chance does not make its "neighbours" relevant). Every result of a search with the model carries `similarity`, `z` and `relevance` (0-1): the greater of the closeness in meaning (0 at z 2, 1 at z 6) and the closeness by words (a passage with all the words counts at least 0.6, one with only some of them 0.25), so a passage that literally contains the searched name is never shown as 0%.

**Less relevant passages.** The neighbours that the relevance filter drops are counted in every search (`weakCount`); with the option `includeWeak` they are added to the results with `weak: true`, and then everything is ordered by the relevance factor, from the most to the least relevant. Passages found by words are never `weak`.

**Words of the vocabulary (local synonyms).** A table `word_embeddings (model, word, vector)` and an FTS5 vocabulary view `chunks_vocab` (the words of the texts, without capitals or accents, with how often they appear). `pendingWords(model, limit)` gives the most frequent words of 4–24 letters without digits that have no vector yet, `storeWordVectors(model, items)` saves them, `wordCount(model)`, `pruneWords()` removes words that no longer appear, `nearestWords(model, vector, { count, exclude })` returns `[{ word, similarity, z }]`: the closest words with the z score against all the others. `clearEmbeddings` also clears the word vectors.
